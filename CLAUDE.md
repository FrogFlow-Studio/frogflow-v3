# Работа с этим репозиторием

FrogFlow v3 — продолжение v2, переписывания платформы из `FrogFlow/frogflow`
(v1). Один деплой на всех клиентов. Прежде чем что-то делать, прочитать
`docs/ARCHITECTURE.md` и `docs/ROADMAP.md`.

**v2 заморожен** (решение Якова, 03.10.2026): он работает в проде, туда идут
только срочные правки. Все новые работы — только в v3. Срочную правку v2 в v3
приносим обычным merge, без перебазирования и без периодической синхронизации.

## Правила

1. **Схема базы не меняется.** v1 и v2 работают на одной базе одновременно,
   клиенты переезжают по одному. Всё новое про клиента — в `bots.settings`
   (jsonb), типизировано в `src/core/tenant/types.ts`.
2. **`process.env` читается только в `src/config/env.ts`.** ESLint это
   проверяет. Окружение описывает платформу; всё про клиента приходит через
   `TenantContext`.
3. **Ядро не знает канала.** `src/core/*` принимает `ctx: TenantContext`
   первым аргументом и не импортирует `src/channels/*`. Адаптер разбирает
   входящее и рисует ответ, бизнес-правила — в ядре, один раз.
4. **Домен ходит в базу через `ctx.db`** (роль арендатора). `serviceDb()` —
   только справочник арендаторов, кроны по всем клиентам, оператор, Storage.
5. **Перенос — по описи.** Перед переносом функции найти её проверки и
   поломки в `docs/inherited-knowledge.md`; сначала тесты, потом код.
6. **Клиент прежней платформы для v2 невидим.** Пока оператор не переключил
   `settings.served_by = "v2"` (`servedByV2` в `core/tenant/directory.ts`),
   v2 не пускает его продавца в админку и покупателей на витрину, не выдаёт
   заказы, не чистит журналы и не трогает вебхуки — заказы и материалы
   такого клиента идут через v1. Любая новая точка входа (маршрут, крон,
   серверная функция) проверяет этот флаг.
7. **Перед пушем — `npm run check`** (lint, typecheck, test) зелёный без
   исключений. `npm run build` перегенерирует `src/routeTree.gen.ts` — его
   коммитим вместе с маршрутами.

## Перед PR

Частые причины возврата PR. Проверьте каждый пункт, прежде чем отдавать PR:

- **«Один раз» — условная запись до отправки.** Отметку («напомнили»,
  «наградили», «уведомили») ставит условное обновление, и только выигравший
  шлёт сообщение или выдаёт награду. Условие — на маленькое поле: версия
  (`rev`), статус, отметка; никогда на весь jsonb или длинный текст: больше
  ~8 КБ в адресе запроса дают 431, и запись молча перестаёт работать. Повтор
  события, двойной клик, два крона одновременно — отдельный тест на гонку.
- **Не затирать чужое.** `bots.settings` меняется через `patchTenantSettings`
  (или с повышением `rev`), `bot_users.state` — точечно или с условием на
  маленькие поля (свой счётчик, `state->>mode`): его пишут и бот, и v1. `loyalty_points` общие с v1 —
  только прибавлять, никогда не пересчитывать.
- **Без молчаливых обрезок.** Никакого `limit(N)`, который тихо теряет
  строки: постранично (`eachPage`/`pageAll`) или `count`. Сортировка
  заканчивается уникальным ключом (`id`; у `bot_users` — `user_key`, у
  `blocked_users` — `bot_id, telegram_id`). Длинные `.in(...)` — кусками по 200.
- **Ошибки базы.** Каждый `error` из select проверяется; «нет данных» ≠
  «не удалось прочитать». Наружу — `serverFailure`, не `new Error` с текстом.
  Особенно перед удалением: упавшее чтение не должно превращаться в «удалить всё».
- **Только v2.** Каждая новая точка входа (маршрут, крон, серверная функция,
  событие вебхука) проверяет `servedByV2`; крон — в `JOBS` в
  `src/lib/cron-route.test.ts`.
- **Роли.** Новая серверная функция админки — в списке ролей (#185,
  `accountant-access.test.ts`), начинается с `requireAdmin()`/`requireOperator()`.
- **Почта покупателя сайта не подтверждена.** Одна почта ничего не открывает:
  ни трат (баллы, промокоды, награды), ни чужих данных. Награда — только за
  реально оплаченный заказ.
- **Деньги видны в журнале.** Любая оплата, переплата или оплата по
  отменённому заказу оставляет событие в истории заказа с суммой и номером
  платежа; «оплачено» не пишется раньше, чем это правда.
- **4 языка.** Каждая строка для продавца и покупателя — ru, kk, en, uz.
- **Текст не обещает больше кода.** Подсказка в интерфейсе, письмо, preflight
  описывают то, что код действительно делает; при изменении поведения — поправить
  и тексты, и проверки переезда (`core/tenant/preflight.ts`).
- **Тест проверяет настоящий путь.** Заглушка не должна подменять проверяемую
  логику: если тест называется «свежая ссылка сработала», в нём она срабатывает
  и результат виден (статус, запись), а не только порядок вызовов.
- **Внешние вызовы.** У каждого `fetch` — тайм-аут (`AbortSignal.timeout`), у
  длинной работы в функции — общий бюджет меньше 120 с. Отправку, которая
  могла дойти (обрыв, тайм-аут, 5xx), не повторять и не дублировать другим
  методом (Telegram, Zernio, почта).
- **Zernio.** Ошибки разбирает только `src/channels/zernio/errors.ts`; 500 и
  таймаут — «неизвестно», вслепую не повторять; поля сверять с
  `/mnt/project-files/zernio/`.
- **Ветка от master, база — master.** PR поверх другого PR — только при
  крайней нужде; после вливания нижнего проверить `base.ref` и переключить на
  master. Перед отдачей влить свежий master. Сид и фикстуры e2e — в своём
  разделе `tests/e2e/seed/*.ts` и `tests/e2e/fixtures/*.ts`; в
  `tests/e2e/seed.ts` и `fixtures.ts` оставлять строки импорта и вызова обеих
  сторон и следить, чтобы тесты не задвоились (Playwright падает на одинаковых
  именах).
- **`npm run precheck` перед каждым PR.** Одна команда: prettier и eslint по изменённым
  относительно `origin/master` файлам, типы, тесты по изменённым, `src/lib` и
  `tests/db-columns.test.ts`, золотые диалоги `tests/dialogs`, сканирующие тесты (подписи аудита, роли, `JOBS` кронов, переводы), всё без ключей Supabase; в конце «готово к PR» или что упало.
  Дважды PR возвращали из-за prettier, один раз master покраснел из-за
  `tests/db-columns.test.ts` (#240). Полный `verify`, сборку и e2e гонит Контрольный.
- **Поломка диалога — сначала сценарий.** Любая найденная ошибка в переписке бота (ответ не туда, молчание, чужой язык, дубль) сначала становится сценарием в `tests/dialogs/scenarios.ts` (поле `origin` — откуда), падает, потом чинится. Прогон `tests/dialogs` входит в `precheck`.
- **Проверки без ключей живой базы.** У новых веток в окружении есть ключи
  Supabase, поэтому `check` запускать так:
  `env -u SUPABASE_URL -u SUPABASE_SERVICE_ROLE_KEY -u SUPABASE_JWT_SECRET npm run check`.
  Живые тесты (`tests/integration`) гоняет только «Живой прогон» по заказу
  интегратора.
- **Тест не зависит от окружения.** Тест, который импортирует маршрут или
  модуль с `env()`, подставляет окружение через `setEnvForTests(...)`: без
  ключей живой базы он иначе падает «Окружение настроено неверно» (#292,
  `operator-api-2fa.test.ts`).
- **e2e перед вливанием, локаторы точные.** Изменение страниц проверяется
  прогоном e2e на сборке. Кнопки и ссылки по имени ищутся с `exact: true`:
  после «Войти через Telegram» 14 из 60 e2e упали на `name: "Войти"` (#292).
- **Отдавая PR интегратору:** номер, коммит, база, что проверено
  (`npm run check`, `npm run build`, e2e) и на что смотреть особо.

## Веб-часть

`src/app/*` — код панелей: `auth/` (сессия, пароли, гварды), `ui/`
(компоненты без зависимостей), `operator/` и `admin/` (серверные функции в
`*.functions.ts`, реализация в `*.server.ts`). Каждая серверная функция
начинается с `requireOperator()` или `requireAdmin()`: маршрутный гейт —
только UX. Страницы в `src/routes/{operator,admin}._authed.*.tsx`.

Ловушка dev-сервера: запросы `<img>` (Sec-Fetch-Dest: image) Nitro в dev
считает статикой Vite и не отдаёт приложению, поэтому картинки из
`/api/img/*` в `npm run dev` показывают 404. В продакшен-сборке всё работает;
проверять так: `NITRO_PRESET=node-server npx vite build && node .output/server/index.mjs`.

## Тесты на живой базе

`tests/integration/*` ходят в настоящую Supabase под ключами из `.env`
(файл в `.gitignore`, шаблон — `.env.example`) и пропускают себя без них.
Пишут они только на демо-клиента «Демо-тестер» и убирают за собой.

## Проверки

```bash
npm run check       # lint + typecheck + test
npm run build       # typecheck + vite build (Nitro, Vercel preset)

# Сквозной прогон в браузере (Playwright) против подставной базы, как в CI:
NITRO_PRESET=node-server npx vite build && npm run e2e
```

Сводку готовности `docs/READINESS.md` в обычных PR не трогаем: тест проверяет
только `docs/readiness.json` (пункты и имена тестов). Сводку пересобирает
отдельный PR (`npm run readiness`); при конфликте в ней берём версию из master.
`docs/readiness.json` правится руками: при конфликте в нём оставляем строки
обеих сторон (и из master, и свои), целиком из master его не берём.
