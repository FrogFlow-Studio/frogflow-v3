# Архитектура FrogFlow v2

Один репозиторий — один деплой. Все клиенты обслуживаются одним приложением,
арендатор определяется из запроса, а не из переменных окружения. База данных
та же, что у v1, схема не меняется — это позволяет переводить клиентов по
одному и откатывать любого из них одной командой.

## 1. Почему v1 требовала деплой на клиента

В v1 клиент — это набор переменных окружения проекта Vercel: `BOT_ID`,
`SUPABASE_TENANT_KEY`, `TELEGRAM_BOT_TOKEN`, `VERTICAL`, `ADMIN_PASSWORD`,
`PUBLIC_APP_URL`, `ZERNIO_PROFILE_ID` и ещё около тридцати. Код читал
`process.env.BOT_ID` в 34 файлах. Всё, что знало «чей это магазин», знало это
из окружения — поэтому второй клиент означал второй проект Vercel, свой
вебхук, свой крон, своё место, где что-то может отстать.

v2 переворачивает это: окружение описывает **платформу** (одна база, один
секрет подписи, один ключ шифрования), а всё про **клиента** лежит в строке
`bots` и приходит в код через `TenantContext`. ESLint-правило запрещает
`process.env` везде, кроме `src/config/env.ts`, чтобы «ещё одна переменная
на клиента» не появилась снова.

## 2. Схема

```
                     ┌──────────────────────────────────────────────┐
  Telegram ─────────▶│ /api/telegram/<bot_id>   secret = HMAC(bot_id)│
  Zernio (IG/WA) ───▶│ /api/zernio/webhook      tenant по accountId  │
  Браузер ──────────▶│ /s/<slug>/…  или свой домен (Host)            │
  Vercel Cron ──────▶│ /api/cron/<job>          обходит всех клиентов│
  Оператор ─────────▶│ /api/operator/*          Basic-auth платформы │
                     └───────────────┬──────────────────────────────┘
                                     │ resolveTenant(lookup)
                                     ▼
                     ┌──────────────────────────────────────────────┐
                     │ TenantContext { tenant, db, appUrl, secrets } │
                     │   db = tenantDb(bot_id): JWT tenant_bot       │
                     │   secrets.telegramToken(): расшифровка        │
                     └───────────────┬──────────────────────────────┘
                                     ▼
        channels/ (тонкие адаптеры)          core/ (домен, канала не знает)
          telegram/   update → команды          tenant/    справочник, JWT
          zernio/     (фаза 4)                  catalog/   товары, категории
          web/        (фаза 5)                  cart/      корзина
                                                orders/    заказ, чек, выдача
                                                pricing/   цена по стране
                                                customers/ покупатели
                                                notify/    получатели
                                                modules/   реестр модулей
                                                verticals/ реестр ниш
```

Адаптер разбирает входящее, зовёт функции ядра, рисует ответ. Ядро принимает
`TenantContext` первым аргументом и не знает, из какого канала пришла команда.
Все бизнес-проверки (смешанная корзина, цифровой товар без файлов, двойной тап
по «Оформить») живут в ядре один раз и работают одинаково во всех каналах —
в v1 они были написаны дважды, по разу на бота, и расходились.

## 3. Арендатор из запроса

`src/core/tenant/`:

- **Справочник** (`resolve.server.ts`): все неархивные строки `bots` в памяти
  на минуту. При десятках клиентов это дешевле jsonb-запросов и не требует
  индексов, которых в схеме нет. Промах по кешу перечитывает базу один раз —
  свежий клиент виден сразу.
- **Сопоставление** (`directory.ts`, чистая функция, покрыта тестами):
  - `id` — из адреса вебхука Telegram и внутренних вызовов;
  - `zernio_account` — `settings.zernio.account_ids` содержит `accountId`
    события;
  - `host` — заголовок Host совпадает с `settings.hosts[]` или с хостом
    `bots.app_url` (у v1-клиентов это их Vercel-адрес);
  - `slug` — `settings.slug` в адресах общего домена `/s/<slug>/…`.
- **Контекст** (`tenantContext(tenant)`): подключение к базе под ролью
  арендатора, публичный адрес, ленивая расшифровка токена.

`bots.settings` (jsonb) расширяется без миграций — ключи, которых v1 не знает,
v1 не мешают. Форма описана в `src/core/tenant/types.ts` (`TenantSettings`).

## 4. Изоляция данных — та же, что в v1, без ключа на деплой

v1 выпускала на каждый деплой JWT с `role: tenant_bot` и `bot_id`
(`scripts/mint-tenant-key.mjs`), и RLS-политики из `MIGRATION-02` резали
каждую строку по claim'у. v2 подписывает такой же JWT **на лету** под того
арендатора, которого нашёл резолвер (`src/core/tenant/jwt.ts`), живёт он час
и кешируется по `bot_id` (`src/core/db/client.server.ts`). Ничего в базе не
меняется: та же роль, те же политики, тот же `current_bot_id()`.

Следствие: код домена с `ctx.db` **физически не может** прочитать чужие
строки, даже если где-то забыт фильтр. `serviceDb()` (service_role) остаётся
только для справочника арендаторов, панели оператора, кронов и хранилища.

Хранилище (Storage) по-прежнему общее, роль `tenant_bot` там не резолвится;
изоляция — префиксом `<bot_id>/` в ключе и проверкой `isOwnStorageKey` на
каждом пути отдачи. Так же было в v1.

## 5. Секреты клиентов

`CONTROL-PLANE-PLAN.md` в v1 решил не хранить токены ботов в базе: у каждого
клиента был свой деплой, который токен и так держал, а панели оставалось
попросить деплой сделать действие через `/api/internal/*`. С одним деплоем
этот аргумент исчезает — тот деплой, что обслуживает бота, и есть панель, и
токен обязан быть доступен коду по `bot_id`.

Поэтому токен Telegram лежит в существующей колонке `bots.bot_token`,
зашифрованный AES-256-GCM ключом платформы `SECRETS_KEY`
(`src/core/secrets/vault.ts`, формат `enc:v1:<iv>:<tag>:<ct>`). Утечки одной
базы недостаточно, нужен ещё ключ из окружения; префикс версии оставлен под
ротацию. Открытый токен в этой колонке v2 не принимает — только `enc:v1:`.

Секрет вебхука Telegram не хранится вовсе: он выводится как
`HMAC(WEBHOOK_SECRET, "telegram:" + bot_id)` и передаётся в `setWebhook` как
`secret_token`. Подделать заголовок без секрета платформы нельзя, ротировать
по одному нечего.

## 6. Маршруты одного деплоя

| путь                          | кто ходит          | арендатор                  |
| ----------------------------- | ------------------ | -------------------------- |
| `POST /api/telegram/<bot_id>` | Telegram           | из адреса, подпись по HMAC |
| `POST /api/zernio/webhook`    | Zernio             | по `accountId` события     |
| `GET /api/cron/<job>`         | Vercel Cron        | обход всех клиентов на v2  |
| `POST /api/operator/bots`     | оператор           | — (service_role)           |
| `GET /api/img/<bot_id>/<key>` | Telegram, браузер  | из адреса, префикс ключа   |
| `GET /api/health`             | мониторинг         | —                          |
| `/s/<slug>/…`, свой домен     | покупатель         | slug или Host (фаза 5)     |
| `/admin`, `/operator`         | продавец, оператор | сессия (фаза 5)            |

Кроны — одна задача на весь деплой, внутри цикл по клиентам; сбой у одного
не останавливает остальных. В v1 каждый деплой гонял свои 15 кронов.

## 7. Модули и ниши

Реестры перенесены из v1 без изменений (`src/core/modules/registry.ts`,
`src/core/verticals/registry.ts`) — это единственный источник списка ключей,
цен и статусов. Разница в чтении:

- флаги модулей — `ctx.tenant.modules[key]`, канонический набор из `bots.modules`
  (ключи реестра, которых нет в строке, выключены);
- ниша — `ctx.tenant.vertical` из колонки `bots.vertical`, которую v1 писала
  только для панели, а рантайм читал из `VERTICAL`. Никаких
  `process.env.VERTICAL` и `if (niche === …)` в общем коде.

## 8. Что перенесено, что нет

Сделано и зелёное (`npm run check`):

- окружение платформы с проверкой при старте (`src/config/env.ts`);
- справочник и резолвер арендаторов, per-request JWT, шифрование токенов;
- ядро: каталог, цены по стране (с ручной ценой и конвертацией), покупатели,
  корзина со всеми гвардами v1, заказ (атомарный захват через
  `claim_order_placement`, снимок позиций и файлов, очистка корзины только
  после вставки позиций), чек (бакет `payment-proofs`, хеш против повтора),
  выдача цифрового заказа с `delivery_index`;
- адаптер Telegram: `/start`, выбор языка, меню, каталог с пагинацией,
  карточка с вариантами, корзина, страна, телефон, оформление по реквизитам,
  приём чека, уведомление продавцу с кнопками, подтверждение/отклонение,
  выдача файлов, «Мои заказы», повторная выдача, гварды блокировки и паузы;
- вебхуки Telegram и Zernio (последний — приём и журнал без обработки),
  крон `ensure-webhook`, API оператора для подключения клиента, скрипт
  `scripts/onboard.mjs`.

Не перенесено — см. `docs/ROADMAP.md`: промокоды, баллы, сертификаты,
«все языки», физические товары (доставка, зоны, даты), Robokassa, OCR чеков,
VIP-бот, магазин в Direct, консультант, Mini App, витрина, админка, панель
оператора, рассылки, чат с менеджером, отзывы, рефералы, напоминания.

Каждый перенос идёт по описи `docs/inherited-knowledge.md`: сначала
проверки из неё, потом код.
