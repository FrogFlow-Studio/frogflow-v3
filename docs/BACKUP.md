# Восстановление базы из бэкапа

Что делать, если боевая база Supabase потеряна или испорчена, и как раз в месяц
убедиться, что бэкап вообще годится. База общая для v1 и v2/v3: потеря бьёт по
всем клиентам сразу, поэтому порядок записан заранее.

Чего здесь нет: настроек самого Supabase. Срок хранения бэкапов и наличие
восстановления на любой момент (PITR) зависят от тарифа проекта — их смотрит
Яков в панели и записывает в таблицу ниже. Код этого не знает.

## Что где лежит

| Что                                                                                     | Где                                                          | В бэкапе базы?                   |
| --------------------------------------------------------------------------------------- | ------------------------------------------------------------ | -------------------------------- |
| Таблицы `public` (46 штук, карта в `docs/db-schema.md`)                                 | Supabase Postgres                                            | да                               |
| Файлы покупателей и магазинов: чеки, материалы, картинки                                | Storage, 7 бакетов (`BUCKETS` в `scripts/snapshot-check.ts`) | **нет**                          |
| Токены ботов и ключи Zernio                                                             | в базе, **зашифрованы** `SECRETS_KEY`                        | да, но без ключа не расшифровать |
| `SECRETS_KEY`, `SUPABASE_JWT_SECRET`, `SESSION_SECRET`, `WEBHOOK_SECRET`, `CRON_SECRET` | переменные Vercel                                            | **нет**                          |
| Вебхуки Telegram и Zernio                                                               | у Telegram и Zernio, указывают на наш домен                  | нет                              |

Из этого два правила:

1. **`SECRETS_KEY` должен лежать ещё в одном месте** (менеджер паролей Якова,
   не в чате и не в репозитории). Бэкап базы без него — это база без токенов
   ботов: придётся просить каждого клиента выпустить токен заново.
2. **Файлы Storage надо копировать отдельно.** Бэкап базы хранит только имена
   файлов, а чек, по которому спорят о деньгах, — файл.

## Что записать один раз (заполняет Яков)

| Вопрос                                          | Ответ |
| ----------------------------------------------- | ----- |
| Тариф проекта Supabase                          |       |
| Сколько дней хранятся ежедневные бэкапы         |       |

Бэкапы смотрятся в панели Supabase, в разделе Database (Backups).

## Если базы нет: порядок

Не торопиться. Пока копия не проверена, боевые переменные не трогаем.

1. **Остановить запись.** Если боевая база ещё жива, но испорчена, остановить
   кроны (убрать блок `crons` из `vercel.json` и сделать Redeploy) и поставить
   магазины на паузу в панели оператора (статус `paused`): иначе бот
   продолжит писать поверх.
2. **Восстановить в новый проект, не поверх боевого.** Восстановление «на
   месте» заменяет базу всех клиентов сразу, и откатить его нельзя. Если
   восстановление в новый проект недоступно, загрузить дамп (`pg_dump` с
   боевой, либо файл бэкапа из панели) в чистый проект Supabase.
3. **Проверить копию** (раздел ниже) и сравнить её с боевой, если та отвечает.
4. **Файлы Storage:** создать в новом проекте те же 7 бакетов с теми же
   настройками (публичность — `docs/db-schema.md`, раздел 3) и залить объекты.
   Пути вида `{bot_id}/…` сохраняются как есть.
5. **Переключить платформу на копию**, только если проверка зелёная:
   в Vercel заменить `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`,
   `SUPABASE_SERVICE_ROLE_KEY` и **`SUPABASE_JWT_SECRET`** (у нового проекта он
   другой: им подписывается ключ арендатора на каждый запрос), сделать Redeploy.
   Клиенты, которые ещё на v1, имеют свои проекты Vercel и свой ключ
   арендатора, подписанный старым секретом: им ключ нужно выпустить заново.
6. **Вебхуки.** Адрес нашего домена не менялся, поэтому Telegram и Zernio
   продолжают стучаться туда же. Проверить у каждого живого клиента кнопку
   «Вебхук Zernio» → «Привязать», если подключены Instagram или WhatsApp.
7. **Сообщить клиентам**, за какой период данных нет (копия старше боевой):
   заказы и оплаты после снимка надо восстановить по переписке и чекам.

## Проверка копии

`scripts/snapshot-check.ts` читает базу и ничего в неё не пишет (только GET).
Ключи он берёт из отдельного файла, а не из командной строки:

```bash
# копия.env — SUPABASE_URL и SUPABASE_SERVICE_ROLE_KEY ВОССТАНОВЛЕННОЙ базы,
# боевая.env — то же для боевой. Файлы не коммитим.
node scripts/snapshot-check.ts --env боевая.env --out боевая.json
node scripts/snapshot-check.ts --env копия.env --ref боевая.json
```

Что проверяется: все 46 таблиц читаются, все 7 бакетов Storage на месте,
счётчики строк не больше, чем в боевой (больше — копия не из этой базы), дата
последнего заказа в копии. Меньше строк, чем в боевой, — нормально: копия
старше, разница в отчёте. Код возврата 1 — копия не годится.

Скрипт не сверяет содержимое строк и файлов. После него вручную:

- открыть админку одного клиента и убедиться, что вход и каталог работают;
- открыть заказ со старым чеком и убедиться, что файл открывается;
- написать боту живого клиента и получить ответ: это и есть проверка
  `SECRETS_KEY`, потому что токен бота читается из зашифрованного поля.

## Учение раз в месяц

Раз в месяц (первое число) выполнить шаги 2–3 на **пробном** проекте, не
переключая платформу, и записать результат здесь:

| Дата | Бэкап от | Итог `snapshot-check` | Кто |
| ---- | -------- | --------------------- | --- |
|      |          |                       |     |

Бэкап, который ни разу не восстанавливали, бэкапом считать нельзя.

## Чего не делать

- Не писать в копию данные клиентов, пока она не стала боевой.
- Не включать кроны и вебхуки, смотрящие на копию, пока боевая жива: два
  экземпляра разошлют покупателям напоминания дважды.
- Не менять схему на копии. Схема общая с v1 (`CLAUDE.md`, правило 1).
- Не присылать ключи и `SECRETS_KEY` в чат и в PR.
