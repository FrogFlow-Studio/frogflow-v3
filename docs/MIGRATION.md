# Переезд клиента с v1 на v2

Клиент переезжает один, за пять минут, с откатом одной командой. Данные не
копируются — база одна, v2 пишет в те же таблицы. Переключается только то,
кто отвечает на вебхуки.

## Что должно быть у платформы v2

Один проект Vercel из этого репозитория с переменными из `.env.example`.
`SUPABASE_*` — те же, что у деплоев v1. `SUPABASE_JWT_SECRET` — тот же
legacy-секрет, которым v1 выпускала `SUPABASE_TENANT_KEY`. Остальные
секреты — новые, `openssl rand -hex 32`.

Проверка: `GET https://<v2>/api/health` → `{ ok: true, tenantsOnV2: 0 }`.

## Чек-лист переезда клиента

Первые кандидаты — магазины цифровых материалов в Telegram без Robokassa,
VIP, Instagram и «все языки» (`multi_language`): их путь целиком перенесён.

### За день до переезда

1. **Готовность в карточке клиента** (панель оператора v2, «Готовность к
   переезду»). Блокирует переключение:
   - включённый модуль, которого в v2 нет;
   - нет токена или Telegram его отверг (getMe);
   - нет реквизитов оплаты (и нет Robokassa);
   - нет логина продавца в v2 — после паузы проекта v1 его админка пропадёт;
   - пустой `admin_chat_id` — чек придёт, а «Подтвердить и выдать» нажать
     некому;
   - заказы в `delivering` — их ведёт крон v1, v2 их не подхватит;
   - подписка просрочена дольше отсрочки при политике «приостановить» —
     ночной крон v2 сразу выключит бота.

   Предупреждения (переезд возможен, но поправить): нет товаров, цифровые
   товары без файлов (в v2 их не купить), нет короткого адреса.

2. **Модули и тариф.** Сверить `bots.modules` с тем, за что клиент платит.
   Назначение тарифа (`subscription_plan`) перезаписывает модули набором
   плана — назначать до переезда только сверив состав; без плана модули
   остаются как есть.
3. **Короткий адрес и витрина.** «Адреса» → короткий адрес: на нём
   `/s/<адрес>` (витрина, Mini App — кнопка «🛍 Магазин», если включены
   `shop` и `telegram_mini_app`) и ссылки на документы.
4. **Логин продавца.** Карточка → «Вход продавца в админку»: логин и пароль для
   `/admin` v2. Передать продавцу вместе с датой переезда.
5. **Токен бота** — `TELEGRAM_BOT_TOKEN` из проекта Vercel клиента в v1.
   BotFather не трогаем.

### Переключение (в тихий час, 5 минут)

1. Переключатель «Обслуживает эта платформа» в карточке клиента или

   ```bash
   APP_URL=https://<v2> OPERATOR_USERNAME=… OPERATOR_PASSWORD=… \
   node scripts/onboard.mjs --bot-id <bots.id> --token <TELEGRAM_BOT_TOKEN> \
     --slug <короткое-имя> --serve v2
   ```

   Скрипт идёт через ту же предполётную проверку: при блокирующих пунктах —
   ответ 409 со списком, клиент остаётся на v1 (`--force` — осознанно
   перевести всё равно). Что происходит: токен шифруется в `bots.bot_token`,
   `settings.served_by = "v2"`, `setWebhook` на `https://<v2>/api/telegram/<bot_id>`
   с подписью, кнопка меню — на витрину v2.

2. **Сразу** поставить проект Vercel клиента в v1 на паузу (Settings →
   Pause). Его крон `broadcast` раз в минуту зовёт `ensureTelegramWebhook` и
   забирает вебхук обратно (v1 считает клиента своим по `bots.app_url`), а
   ещё дублирует рассылки и выдачи. Пауза же выключает админку v1 — поэтому
   логин в v2 обязателен заранее.
3. Проверить в карточке: вебхук `ok`, `pending` не растёт.
4. **Проверить руками** в боте: `/start`, каталог, карточка товара, корзина,
   страна, телефон, оформление, реквизиты, фото чека → у продавца «Подтвердить
   и выдать» → файлы у покупателя. Продавец входит в `/admin` v2 и видит заказ.

Покупатели, которые были посреди оформления, продолжают без потерь: формат
`bot_users.state`, корзины и заказов общий, кнопки v1 (`cat:`, `prod:`,
`add:`, `checkout`, `country:`, `confirm:`, `reject:` и др.) v2 понимает.
Не понимает `lang_<язык>:…` (выбор языка материалов в v1) и `searchmore:` —
поэтому клиенты с `multi_language` пока не первые.

## Откат

1. `node scripts/onboard.mjs --bot-id <bots.id> --serve v1` (или
   переключатель в карточке). v2 возвращает кнопке меню стандартный вид и
   на обновления этого бота отвечает `503`: Telegram держит их у себя, а не
   теряет.
2. Снять паузу с проекта Vercel клиента в v1. Его крон в течение минуты
   ставит вебхук на v1, и Telegram отдаёт ему накопленные обновления.
3. Свою кнопку меню Mini App v1 ставит при перезагрузке настроек
   (`/api/internal/reload` деплоя v1, его зовёт панель оператора v1 при смене
   модулей). У покупателей в старых сообщениях может остаться кнопка
   «🛍 Магазин» на витрину v2 — она покажет, что магазин недоступен.

Токен в `bots.bot_token` остаётся зашифрованным, v1 эту колонку не читает.
Заказы, оформленные в v2, v1 видит сразу — база одна.

## Что видно в обеих версиях одновременно

После переезда продавец работает в админке v2 (`/admin`): v2 пускает туда
только клиентов с `served_by = "v2"`. Панель оператора v1 по-прежнему может
менять модули и паузу — v2 читает `bots.modules` и `bots.status` с
задержкой до минуты. «Переустановить webhook» в панели v1 вернёт клиента на
v1 — пока клиент на v2, кнопку не нажимать.

## Сторис-теги консультанта

Таблица v1 `story_product_tags` (bot_id TEXT, без RLS) ядром v2 не
читается. При переключении `served_by = "v2"` оператор один раз копирует
строки клиента в `app_settings.consultant_story_tags`
(`importLegacyStoryTags` в `app/operator/operator.server.ts`); если у клиента
в v2 теги уже есть, импорт пропускается.
