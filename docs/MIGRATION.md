# Переезд клиента с v1 на v2

Клиент переезжает один, за пять минут, с откатом одной командой. Данные не
копируются — база одна, v2 пишет в те же таблицы. Переключается только то,
кто отвечает на вебхуки.

## Что должно быть у платформы v2

Один проект Vercel из этого репозитория с переменными из `.env.example`.
`SUPABASE_*` — те же, что у деплоев v1. `SUPABASE_JWT_SECRET` — тот же
legacy-секрет, которым v1 выпускала `SUPABASE_TENANT_KEY`. Остальные
секреты — новые, `openssl rand -hex 32`.

Проверка: `GET https://<v2>/api/health` → `{ ok: true, tenantsOnV2: 0 }`.

## Перевод клиента

1. **Убедиться, что клиент помещается в перенесённое.** Карточка клиента в
   панели оператора показывает «Готовность к переезду»: включённые модули,
   которых в v2 ещё нет, токен (getMe), реквизиты, товары, логин продавца.
   Переключатель «Обслуживает эта платформа» не включится, пока есть
   блокирующие пункты. Первые кандидаты — магазины цифровых материалов без
   Robokassa, VIP и Instagram.

2. **Токен бота** — тот, что лежит в `TELEGRAM_BOT_TOKEN` проекта Vercel
   клиента (Vercel показывает переменные владельцу проекта). Токен не
   меняется, BotFather не трогаем.

3. **Подключить:**

   ```bash
   APP_URL=https://<v2> OPERATOR_USERNAME=… OPERATOR_PASSWORD=… \
   node scripts/onboard.mjs --bot-id <bots.id> --token <TELEGRAM_BOT_TOKEN> \
     --slug <короткое-имя> --serve v2
   ```

   Что произойдёт: `getMe` проверит токен; токен зашифруется в
   `bots.bot_token`; `settings.served_by = "v2"`; `setWebhook` переставит
   вебхук на `https://<v2>/api/telegram/<bot_id>` с подписью. С этой секунды
   обновления Telegram идут в v2. Ответ команды содержит `webhook.ok`.

4. **Проверить руками** в боте клиента: `/start`, каталог, карточка, корзина,
   оформление, чек, кнопка «Подтвердить и выдать» у продавца, файлы.

5. **Остановить крон v1 для этого клиента.** Деплой v1 каждый час зовёт
   `ensure-webhook` и ставит вебхук обратно, если `bots.app_url` совпадает с
   его адресом. Проще всего — поставить проект Vercel клиента на паузу
   (Settings → Pause) или удалить крон в его `vercel.json`. Удалять проект
   до конца проверки не нужно: он и есть откат.

## Откат

```bash
node scripts/onboard.mjs --bot-id <bots.id> --serve v1
```

и в панели оператора v1 — «Переустановить webhook» (или снять паузу с
проекта Vercel: его крон вернёт вебхук в течение часа). v2 после этого
отвечает Telegram `200` без обработки — очередь не копится, клиент снова на
v1. Токен в `bots.bot_token` остаётся зашифрованным, v1 эту колонку не читает.

## Что видно в обеих версиях одновременно

Пока клиент на v2, его **админка** остаётся на деплое v1 (до фазы 5): она
читает те же таблицы, поэтому заказы, оформленные через v2, видны в v1 сразу.
Панель оператора v1 продолжает управлять модулями и паузой — v2 читает
`bots.modules` и `bots.status` с задержкой до минуты.

Одно ограничение: «Переустановить webhook» в панели v1 вернёт клиента на v1.
Кнопку не нажимать, пока клиент на v2.

## Сторис-теги консультанта

Таблица v1 `story_product_tags` (bot_id TEXT, без RLS) ядром v2 не
читается. При переключении `served_by = "v2"` оператор один раз копирует
строки клиента в `app_settings.consultant_story_tags`
(`importLegacyStoryTags` в `app/operator/operator.server.ts`); если у клиента
в v2 теги уже есть, импорт пропускается.
