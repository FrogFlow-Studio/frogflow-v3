# Генеральная репетиция переезда

Цель — пройти путь из `docs/MIGRATION.md` целиком на «Демо-тестере»:
проверка перед переездом → переключение → работа в Telegram, Instagram и на
сайте → откат, и убедиться, что после отката клиент такой же, каким был.
Настоящих клиентов и v1 репетиция не трогает.

Кто делает: сценарий — этот файл. Прогон заказывает интегратор, выполняет
«Живой прогон», по одному, когда никто другой не гоняет живые тесты. Часть Б
на проде без Якова не начинается: там нужен тестовый бот, токен которого
Яков вводит сам в панели оператора (через чат токены не передаём).

## Правила прогона

- Ключи базы — только переменные окружения оболочки, никуда не
  записываются и не выводятся.
- Пишем только в строки «Демо-тестера» (`DEMO_BOT` в
  `tests/integration/live.ts`). Остановиться при любой ошибке, которая
  называет другой `bot_id`.
- Перед стартом сказать интегратору, что живые тесты заняты; после — что
  свободны.
- Любой шаг упал — не чинить руками в базе, а остановиться, выполнить
  «Уборку» и прислать интегратору номер шага, вывод и снимки.

## 0. Подготовка

1. Свежий master: `git pull`, `npm ci`, `npm run check` зелёный.
2. Сборка как на проде не нужна: часть А идёт через код v2 напрямую.

## 1. Снимок «до» (только чтение)

Сохранить в файл вне репозитория (без секретов):

- `bots` демо: `status`, `modules`, `subscription_plan`,
  `subscription_expires_at`, `owner_telegram_id`, `settings.served_by`,
  `settings.billing`, `settings.multi_bot`, `settings.telegram`, отпечаток
  `bot_token` (sha256 зашифрованного значения, не само значение);
- для возврата после части Б: зашифрованное `bots.bot_token` демо и
  `settings.telegram` — только в переменную оболочки на время прогона, не в
  файл и не в отчёт;
- `app_settings` демо: список ключей и значение `admin_chat_id`;
- `bot_users` демо: число строк, сумма `loyalty_points`, отпечаток пар
  «telegram_id — баллы» (sha256 отсортированного списка);
- `orders` демо: число по статусам; `products`, `payment_methods`: число
  активных;
- `zernio_logs` и `bot_events` демо: число строк.

## Часть А. Живая база, код v2 (автоматически)

3. `npx vitest run tests/integration/migration-rehearsal.test.ts` — все
   тесты зелёные. Проверяет:
   - пока клиент на v1, ни один крон v2 его не видит;
   - проверка перед переездом называет, чего не хватает; без чата продавца
     `onboard` отвечает 409 и клиент остаётся на v1;
   - `onboard` переводит на v2 и ставит вебхук с подписью;
   - после переезда модули, тариф, связь ботов, покупатели и баллы те же;
   - покупатель проходит заказ через вебхук Telegram, продавец
     подтверждает, файл уходит;
   - откат: кнопка меню стандартная, вебхук v2 отвечает 503.
4. `npx vitest run tests/integration/migration.test.ts` — зелёный (то же
   переключение через `setServedBy` панели оператора).
5. Каналы на живой базе:
   `npx vitest run tests/integration/zernio-shop.test.ts tests/integration/zernio-whatsapp-shop.test.ts tests/integration/telegram-order.test.ts`
   — покупка в Direct, WhatsApp и Telegram до выдачи. Эти тесты зовут ядро
   напрямую, мимо проверки `served_by`, поэтому сам переезд для каналов
   Zernio и сайта проверяет часть Б.
6. Снимок «после А» по пункту 1 совпадает со снимком «до». Любое расхождение
   — стоп и в отчёт.

## Часть Б. Прод www.frogflow.tech (с Яковом)

Нужно заранее: тестовый бот в BotFather, Instagram тестового аккаунта,
привязанный в Zernio к «Демо-тестеру» (если его нет — шаги Instagram
пропускаются и помечаются в отчёте), логин продавца демо.

7. **Проверка перед переездом.** Панель оператора → карточка «Демо-тестера»
   → «Готовность к переезду». Сверить с ожиданием: блоков нет, либо только
   те, что закрываются шагом 8. Снимок экрана — в отчёт.
8. **Переключение.** Яков вводит токен тестового бота в карточке и включает
   «Обслуживает эта платформа: v2». Если у демо есть Instagram — сразу
   «Привязать» в карточке «Вебхук Zernio» в «Настройках платформы».
   Ожидание: вебхук `ok`, `pending` не растёт.
9. **Telegram.** В тестовом боте: `/start`, каталог, карточка, корзина,
   страна, оформление, фото чека → у продавца «Подтвердить и выдать» → файл у
   покупателя. Продавец входит в `/admin` и видит заказ.
10. **Instagram.** Сообщение в Direct тестового аккаунта → каталог → заказ →
    чек → подтверждение в админке → ссылка на материалы в Direct. Один
    ответ продавца из «Чата» доходит.
11. **Сайт.** Если у демо выключены модуль `web_storefront` или оформление
    на сайте (настройка `storefront_checkout` в админке продавца), включить
    их на время прогона и записать в отчёт. `/s/<адрес демо>` открывается,
    заказ с оплатой переводом и чеком проходит до материалов на странице
    заказа.
12. **Откат.** Переключатель → v1. Ожидание: вебхук Telegram v2 отвечает 503
    (Telegram держит обновления у себя), `/s/<адрес демо>` больше не открывает
    витрину, события Instagram демо v2 больше не обрабатывает.
13. **Вернуть как было:**
    - токен: шаг 8 записал в `bots.bot_token` демо токен тестового бота. Вернуть
      в строку демо прежнее зашифрованное значение и `settings.telegram` из
      переменной оболочки (если токена не было — `bot_token = null`, без
      `settings.telegram`). Отпечаток `bot_token` совпадает со снимком «до».
      Без этого демо останется с чужим токеном, и живые тесты на нём пойдут в
      тестовый бот;
    - `web_storefront` и `storefront_checkout` — как в снимке «до»;
    - тестовый бот можно удалить в BotFather только после возврата токена.

## Уборка и отчёт

14. Удалить заказы, покупателей и события, созданные в части Б (по
    `telegram_id` и `user_key` тестовых покупателей, только `bot_id` демо).
    Часть А убирает за собой сама.
15. Снимок «после» по пункту 1 совпадает со снимком «до», кроме строк,
    которые перечислены в отчёте как оставленные намеренно.
16. Отчёт интегратору: номер каждого шага — прошёл или нет, вывод упавших
    тестов, три снимка (до, после А, после), что пропущено и почему.

Репетиция считается пройденной, когда шаги 3–6 и 7–12 зелёные (шаг 10 — если
Instagram привязан) и снимки совпали.
