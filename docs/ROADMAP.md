# План переноса

Порядок — от самого маленького клиента к самому большому, по одному, с
откатом одной командой (`docs/MIGRATION.md`). Каждая фаза самостоятельно
полезна и не ломает предыдущие.

Правила из `frogflow/docs/v2/README.md` действуют: база не трогается, v1 и
v2 работают одновременно, поломку у живого клиента чиним в v1, готовность
меряется проверками из `docs/inherited-knowledge.md`, а не ощущением. Счётчик — `docs/READINESS.md`
(`npm run readiness`, сопоставление «проверка → тест» в `docs/readiness.json`).

## Фаза 1 — фундамент ✔

Арендатор из запроса, per-request JWT, шифрование токенов, реестры модулей и
ниш, вебхуки, крон вебхуков, API оператора. Готово, `npm run check` зелёный.

## Фаза 2 — цифровой магазин в Telegram ✔ (минимальный контур)

Каталог → корзина → страна → телефон → заказ → реквизиты → чек → продавец →
выдача. Первый клиент на v2 — самый маленький магазин цифровых материалов
без платных модулей.

## Фаза 3 — оплата и физические товары ✔

Сделано: Robokassa из бота (`/api/robokassa/<bot_id>/<result|success|fail>`,
подпись с `Shp_bot`, настройки в админке), физический чекаут целиком (тип
получения, дата с `lead_time_days`, зоны и комиссия, адрес, примечание,
задаток и `on_receipt`), статусы `accepted → in_production → ready →
delivered` в боте и админке, напоминание за сутки покупателю и продавцу
(`/api/cron/fulfillment-reminder`), автопроверка чеков (Google Vision +
текст из PDF, правила в `src/core/receipts/pure.ts`, переключатель и
счётчик в настройках). Для переезда кондитерских и цветочных — работа
продавца с физическим заказом (`src/core/orders/physical-admin.ts`): заказ
вручную (`platform = manual`, синтетический покупатель по телефону),
«Внести оплату» с учётом `paid_amount`, задаток по чеку при «Принять
заказ» без повторной записи, правка даты/адреса и доставка ↔ самовывоз с
пересчётом комиссии, фильтр «к выдаче» (сегодня, завтра, просрочено, без
даты).

Как было в v1: Robokassa (`robokassa.server.ts`, колбэки `result/success/fail`, подпись по
`robokassa_test_mode`, не по `IsTest`), OCR чеков (Google Vision, `proof_auto`
для RU/KZ), выбор способа оплаты для KZ; физический чекаут (тип получения,
дата с `lead_time_days`, зоны с конвертацией комиссии, адрес, примечание),
статусы `accepted → in_production → ready → delivered`, напоминание за сутки,
`payment_mode = on_receipt`. Ниши `confectionery` и `flowers`.

## Фаза 4 — Zernio: Instagram Direct и WhatsApp ✔ (консультант, чат, магазин)

Сделано: адаптер `src/channels/zernio` — разбор события, покупатель с
синтетическим `telegram_id`, реплика в «Чат» и перехват менеджером из
панели, ИИ-консультант (общий с Telegram, `src/core/consultant`) с проверкой
«менеджер отвечает из приложения» по хвосту переписки, заявка продавцу в
Telegram, ответ менеджера из панели через Zernio, `Idempotency-Key` из
контекста события, журнал `zernio_logs` с итогом обработки. Аккаунты клиента
— в `bots.settings.zernio.account_ids` (ставит оператор), ключ API Zernio
один на платформу.

Магазин в переписке (`dm_shop` / `wa_shop`, `shop-flow.ts` + `shop.server.ts`):
каталог и товары нумерованными списками, номер товара из поста («018»,
«№18»), карточка с фото и кнопками (до трёх), корзина с «убрать N»,
оформление (страна номером/названием/кодом, телефон только для физического
заказа, способ и дата получения, зона/адрес, пожелания), реквизиты с QR
или ссылка Robokassa, чек вложением с автопроверкой OCR, выдача ссылками в
ту же переписку (и по кнопке продавца в Telegram, и из админки),
«мои заказы», выход словом на любом шаге, команды по целому сообщению,
жалоба на оплату — сразу человеку, подавление повторов одного ответа.

Подключение из админки (карточка «Instagram и WhatsApp» в настройках,
`channels/zernio/connect.server.ts`): у клиента свой профиль Zernio,
ссылка авторизации с возвратом на `/admin/settings?zernio=connected`,
синхронизация аккаунтов профиля в `bots.settings.zernio` (снимок для
панелей + `account_ids` для вебхука; ручные id оператора сохраняются).
Вебхук платформы — один на ключ Zernio, чинится кроном `ensure-webhook`,
чужой деплой (v1 клиента) без `force` не перетягивается.

Паритет Instagram с v1 (перенесено): **настройки автоответчика** канала
(`core/instagram/direct-bot-settings.ts`, карточка «Автоответчик» в настройках)
с теми же ключами `app_settings`, что в v1 — `instagram_direct_bot_*` /
`whatsapp_bot_*`: `enabled` (выключенный бот молчит, консультантские ниши
тумблер не читают), `scope` («только по заказам» — вне сценария покупки бот
не отвечает, диалог остаётся непрочитанным; «на все сообщения»), `triggers`
(слова-вызовы сверх встроенных команд), `script` (ответ на непонятное вместо
стандартного), `features` (каталог, поиск, корзина, оформление — выключенная
часть не отвечает ни на команду, ни на кнопку). **Сторис-теги консультанта**
(`core/consultant/story-tags.ts`, карточка «Сторис» у консультанта): тег
«сторис/рилс/пост → товар» в `app_settings.consultant_story_tags`; ответ
покупателя на сторис распознаётся из метаданных события Zernio
(`storyId`/`storyMediaUrl` в `parseZernioMessage`), консультант получает
товар в контексте. Теги из v1 (`story_product_tags`) оператор копирует при
переезде. **Добор зависших событий** — крон `health`
(`channels/zernio/dispatch.server.ts`): событие `received` старше трёх минут
прогоняется тем же обработчиком; старше суток — закрывается без ответа (окно
переписки закрыто); строка, которую прошлый добор забрал и не закрыл за
10 минут, — сбой без повтора (второй прогон дважды позвал бы консультанта и
написал продавцу). Не перенесено намеренно: стартовая подсказка WhatsApp (v2
вместо неё спрашивает язык).

**Поиск консультанта по каталогу** (`core/consultant/catalog-search.ts`,
`catalog-tool.server.ts`; перенос из консультанта BOVI v1): у клиента с большим
каталогом оператор включает «Поиск по каталогу» в карточке клиента
(`bots.settings.consultant_search`). Тогда в подсказке только карта
ассортимента (категория, позиций, цена «от»), а товары, цены и наличие модель
берёт инструментами `search_products` / `get_product` — до 4 раундов на
сообщение, последний без инструментов. Размер сравнивается парой сторон без
порядка с допуском 3 см, широкий запрос отдаёт сводку без карточек, мимо
бюджета — самая дешёвая позиция той же выборки. Цена в ответе сверяется с
найденным (price-check), расход — сумма всех раундов. Без флага — прежний
режим, первые 120 товаров в подсказке. Защиты режима: общий потолок 35 с на все вызовы
модели (таймаут каждого — по остатку, повтор — только если остатка хватит
на два вызова), бронь дневного предела сразу на все раунды, лимит частоты
вызовов ИИ (`core/consultant/rate.server.ts`: 60 в минуту на клиента — общий
счёт, 600 на экземпляр функции), цены карты, бюджета и карточек — через
`resolvePrice` (акции, валюта), каталог в памяти на минуту. Не успел, упёрся
в лимит или не прочитал каталог — вопрос уходит менеджеру. В том же режиме консультант помнит, что покупатель
уже сказал (инструмент `remember_customer`, `state.consultant.profile`, в
данных диалога — «Что известно о покупателе»), и покупку без телефона
менеджеру не передаёт: первый вызов передачи возвращает модели просьбу
спросить телефон и способ получения, второй раз не спрашивает
(`core/consultant/memory.ts`).

**Публикации** (раздел админки «Публикации», модуль `instagram`,
`channels/zernio/posts.server.ts`, правила — `core/social/post-draft.ts`):
пост (фото, карусель до 10), Reels (одно видео) и сторис в один или несколько
аккаунтов Instagram клиента — сразу или по расписанию до 30 дней. Файлы — через
`/api/admin/upload` под префиксом клиента, Zernio забирает их по подписанной
ссылке, живущей до публикации и ещё двое суток. Каждая публикация — строка
`post.created` в `zernio_logs`: по ней список с живым статусом из Zernio,
снятие запланированного (только своего) и защита от повтора той же
публикации в течение 10 минут. В v1 публикаций не было.

**ИИ-помощник продавца** (`core/assistant`, `app/admin/assistant.functions.ts`):
кнопка «Написать с ИИ» под описанием товара и «Пост в Instagram» из карточки
товара — черновик подписи и первое фото в «Публикациях». Текст только
попадает в поле, сохраняет или публикует продавец. Модель та же, что у
консультанта (`CONSULTANT_MODEL`, по умолчанию Haiku 4.5); расход входит в
дневной предел в долларах консультанта, плюс 40 черновиков в день на магазин
(`seller_assist_daily`). Ответа на отзыв пока нет.

**Отзывы в админке** (`/admin/reviews`, модуль «Оценка после покупки»,
`core/reviews/admin.ts`): оценки и комментарии покупателей с товаром и
покупателем, фильтр по оценке и «только с текстом», средняя оценка. Ответ
уходит покупателю личным сообщением в его канал (Telegram или диалог
Instagram/WhatsApp); черновик ответа пишет ИИ-помощник (задание `review`,
тот же дневной предел). Отдельной колонки для ответа нет — схема не меняется,
отправка видна в журнале действий.

**Приписка продавца к выдаче** (`core/delivery/note*.ts`, поле в «Настройках»
при модуле Instagram или WhatsApp, `app_settings.delivery_email_note` — ключ
v1, у переехавших клиентов текст сохраняется): последний абзац сообщения
«заказ выдан» в Direct и WhatsApp — в переписке, из админки и по кнопке в
Telegram. Пустая приписка — текст по умолчанию про «Спам», как в v1. В Telegram
приписки нет, как в v1.

**Шаблоны ниш** (`core/templates`): пустой магазин на «Обзоре» может
«Добавить примеры» — категории и 2–3 скрытых примера товаров своей ниши
(цифровые материалы, кондитерская, цветы, консультант) на русском или
казахском, с пометкой «Пример · » в названии. Покупатель их не видит, продавец
правит и включает; повторно в непустой магазин шаблон не кладётся.

**Водяной знак на PDF** (`core/delivery/watermark*.ts`, переключатель в
«Настройках», `bots.settings.delivery.pdf_watermark`): при выдаче каждый PDF
из хранилища заменяется копией, где на каждой странице написаны покупатель
(имя латиницей, @логин или почта) и номер заказа. Копия одна на заказ и файл
(`<bot_id>/wm/…` в `product-files`), так выдают бот, Direct/WhatsApp,
библиотека витрины и письмо. Файл больше 50 МБ, зашифрованный PDF или сбой —
выдаётся оригинал, ошибка уходит в Sentry. В v1 знака не было. Копии
чистит ночной крон retention: только клиенты v2, только ключи формата копии
в `<bot_id>/wm/` старше 21 дня и не упомянутые как оригинал товара или заказа;
на копию старше 7 дней новая ссылка не выдаётся — она пишется заново.

**Загрузка файлов из админки** (`/api/admin/upload`, правила —
`core/storage/upload.ts`, браузерная часть — `app/admin/upload-client.ts`):
файл идёт из браузера прямо в Storage по подписанной ссылке, как в v1, а не
через функцию Vercel с её лимитом тела запроса 4,5 МБ. Сервер выдаёт ссылку
на новый ключ под префиксом клиента (`sign`), после загрузки сверяет размер и
тип того, что легло в бакет, и удаляет неподходящее (`confirm`). Картинки до
20 МБ, материалы и видео до 200 МБ. `/api/img` отдаёт с нашего домена только
картинки, остальное — как скачиваемый файл.

Паритет WhatsApp с v1 (перенесено): **корзина из каталога Meta**
(`core/whatsapp/native-cart.ts`) — позиции штатной корзины WhatsApp
сопоставляются с товарами админки по retailer id (id товара, номер или
название): совпало — в корзину и сразу к оформлению, не совпало — продавцу в
Telegram текстом, покупателю «передал». **Вне 24-часового окна**
(`channels/zernio/outbox.server.ts`): отказ WhatsApp на обычную отправку →
письмо первым по номеру одобренным шаблоном из настройки
`whatsapp_bot_notify_template` («имя:язык», текст — параметр) или служебным
Direct Send. **Исключённые номера** (`core/whatsapp/exclusions.ts`,
`whatsapp_bot_ignore_excluded_contacts`) — бот не отвечает номерам из списка
исключений, +7 и 8 считаются одним номером. **Кнопки шаблонов Meta** — до трёх
(быстрый ответ, ссылка, звонок) в форме шаблона, компонент BUTTONS. Не
перенесено: статусы доставки сообщений в журнал — Zernio таких событий не
присылает.

Магазин в Direct/WhatsApp, доработки: **копия материалов на почту**
(`core/mail/mail.server.ts` через SMTP платформы, `core/orders/email.ts`) —
после выдачи заказа из Instagram/WhatsApp покупателю с почтой уходит письмо
с подписанными ссылками на 7 дней (ссылки в переписке теряются в ленте);
итог — в таймлайне заказа (`email_sent` / `email_failed`), без SMTP или почты
шаг пропускается. **«Повторить заказ»** (`reorderIntoCart` в
`core/orders/orders.ts`) — кнопка в «моих заказах» Telegram и Direct кладёт
товары закрытого заказа в корзину; снятых с продажи не будет. Оплата по
ссылке (Robokassa) и повтор выдачи при сбое (outbox) уже были.

Настройки продавца (карточка «Магазин»): **валюта магазина** (`shop_currency`
— по умолчанию для новых товаров, реквизитов и витрины), **часовой пояс**
(`bots.settings.timezone`, читается контекстом арендатора вместо
`APP_TIMEZONE`: даты выдачи, напоминания, выгрузки), **подзаголовок и
акцентный цвет витрины** (`shop_tagline`, `storefront_accent` → CSS-переменная
`--accent` на `/s/…`). Реквизиты по странам и юридические тексты были раньше.

Уведомления продавцу (`core/notify/prefs.ts`, карточка «Уведомления»):
матрица «событие → канал» (Telegram, почта через SMTP платформы) для восьми
видов событий, тихие часы в поясе магазина (срочное — заказ, чек, жалоба,
сбой выдачи — приходит всегда, остальное откладывается в `zernio_logs`
`digest:<uuid>`), утренний дайджест в выбранный час (`core/notify/digest.ts`,
крон `health`): заказы за сутки, ожидающие подтверждения, недоставленное,
всё отложенное за ночь. Все точки `notifyAdminsHtml` передают вид события;
уведомление о заказе учитывает тумблер Telegram и почту.

Панель оператора: фильтры списка по платформе (v1/v2) и статусу; страница
**«Переезд на v2»** (`preflightAll` + `setServedByBulk`) — предполётная
проверка всех клиентов на v1 и массовое переключение готовых, каждый
проходит ту же проверку, что и в карточке; **«Журнал действий»** — `bot_events`
по всем клиентам с фильтрами по клиенту и виду; **«Кроны»**
(`app/operator/cron-status.server.ts`) — каждый крон пишет в
`operator_settings` (`cron:<job>`) время, итог, длительность, сводку и
ошибку, страница подсвечивает «молчит» старше двух интервалов.

Mini App, сверка с v1 экран за экраном. В v1 Mini App — отдельный
серверный HTML с чекаутом, чеком, библиотекой и заказами внутри окна; в v2
Mini App — та же витрина `/s/:slug`, открытая кнопкой бота: каталог с поиском
и категориями, карточка (варианты, языки файлов, рейтинг, похожие),
корзина; «Оформить» переносит позиции в корзину бота (`miniAppCheckoutFn`,
initData подписан токеном), оплата, чек, скидки и выдача — в чате бота (там
же промокоды, баллы, сертификаты). Добавлено для паритета: **«Мои заказы»
и «Мои материалы»** внутри Mini App (`/s/:slug/orders`, `miniAppOrdersFn`) —
список заказов со статусами и выданные файлы подписанными ссылками на 7
дней. Не переносится намеренно: чекаут и загрузка чека внутри окна
(дублировали бы бот). Сценарий Playwright `pw/e2e-miniapp.mjs`: каталог →
товар → корзина → оформление (handoff в Telegram), страница заказов вне
Telegram и с подставленным WebApp; оплата и выдача покрыты живыми тестами
бота (`tests/integration/order-events`, `zernio-shop`).

Реестр модулей: `admin_roles` и `notify_in_bot` переведены в `available`
(команда с ролями и матрица уведомлений сделаны); остальные `planned`
переводятся по мере реализации.

Новые модули. **Лист ожидания** (`waitlist`, требует `stock`,
`core/waitlist/waitlist.ts`): на товаре без остатка в Telegram и Direct —
кнопка «Сообщить о поступлении», подписка в `bot_users.state.waitlist`;
когда товар снова в продаже (остаток из нуля стал больше, или товар снова
включён), `saveProductFn`/`setProductActiveFn` рассылают ждущим сообщение на
их языке и снимают подписку у тех, кому оно ушло. В редакторе товара —
сколько человек ждут.

**Ограниченные предложения** (`limited_offers`, `core/offers/offers.ts`):
скидка в процентах на товар до даты и, по желанию, на N штук; хранятся в
`app_settings.limited_offers`, применяются внутри `resolvePrice` — сразу в
боте, Direct, витрине и при оформлении; проданное — по позициям заказов с
начала акции (отклонённые и отменённые не в счёт), кеш на минуту. В карточке
бота и Direct — «🔥 −20% до 30.09 23:59 · осталось 5». Управление — карточка
на странице «Скидки».

**Апсейл** (`upsell`, `core/upsell/upsell.ts`): в корзине Telegram и Direct —
«С этим часто берут» до трёх товаров: правила продавца «товар → что
предлагать» (`app_settings.upsell_rules`, карточка в редакторе товара), без
правил — популярные из той же категории; только в продаже, на складе, не в
корзине и того же вида (цифровое к цифровому). Цена — через `resolvePrice`,
то есть с акциями.

**Возвратные продажи** (`winback`, `core/winback/winback.ts`): серия из двух
сообщений тем, кто давно не заказывал — через `days1` дней после последнего
заказа и, если не вернулся, через `days2`; подстановки `{name}` и `{promo}`
(промокод проверяется при сохранении). Прогресс — `bot_users.state.winback =
{order_id, step}`: новый заказ сам сбрасывает серию. Крон
`fulfillment-reminder` раз в час, только днём по поясу магазина, до 50
сообщений за проход, заказы старше 180 дней не трогаем. Настройка — карточка
на странице «Рассылки».

**Оплата Telegram Stars** (`telegram_stars`, `core/payments/stars.ts`): кнопка
«⭐ Оплатить звёздами (N)» среди способов оплаты, счёт `sendInvoice` в XTR;
число звёзд — сумма к оплате, делённая на курс продавца «1 ⭐ = X» в валюте
магазина (`app_settings.stars_rate`), с округлением вверх. `pre_checkout_query`
пропускает только свой заказ в статусе «ждёт оплаты» с той же суммой;
`successful_payment` → `markPaidOnline` и выдача тем же путём, что после
Robokassa. Вебхук бота теперь подписан и на `pre_checkout_query`: крон
`ensure-webhook` сверяет `allowed_updates` и переставляет вебхук у уже
подключённых ботов.

**Интеграция с CRM и Таблицами** (`crm_integration`, `core/crm/webhook.ts`):
события заказа (создан, чек, выдан, сбой выдачи, отклонён, смена статуса)
из `recordOrderEvent` уходят POST-запросом JSON на адрес продавца — вебхук
amoCRM/Битрикс24, Google Apps Script, Make, Zapier. Доставка — через outbox
(`target.channel = webhook`): повторы с паузой и «Не доставлено». Подпись
`X-FrogFlow-Signature: sha256=HMAC(тело)`, адрес — только https и не во
внутреннюю сеть (проверяется при сохранении и перед каждой отправкой),
редиректы не следуются. Карточка в настройках с тестовым событием.

**Воронка сделок** (`crm_pipeline`, `core/pipeline/`, страница
`/admin/pipeline`): шесть этапов — новая, в работе, ждёт оплаты, оплачена,
выполнено, потеряна. Заказ стоит на этапе своего статуса (`orderStage`),
руками его по доске не двигают. Заявки без заказа — строки `app_settings`
`crm:lead:<id>` (запись `updateSettingAtomic`): продавец заводит их сам
(звонок), а передача от ИИ-консультанта заводит заявку покупателя
(`leadFromHandoff`, одна на покупателя). Когда покупатель заявки оформил
заказ позже неё, на доске остаётся заказ. Закрытые показываются 30 дней,
закрытые заявки старше 90 дней чистит ночная уборка. Модуль входит в Pro и
Business всех ниш (решение Якова), на Basic подключается отдельно по цене
каталога. Тысячи
заявок на магазин потребуют своей таблицы (смена схемы — решение Якова).

**Автоворонка** (`funnel`, `core/funnel/funnel.ts`): до 10 шагов «через N
часов после первого контакта — текст, кнопка «Каталог» по желанию»; отсчёт
от `bot_users.created_at`, прогресс — `state.funnel.step`, покупатели старше
45 дней в серию не попадают. Опоздавшие шаги не шлются пачкой — уходит только
последний наступивший. Сделавший заказ выходит из серии (`stopOnOrder`).
Крон `fulfillment-reminder` раз в час, днём по поясу магазина. Настройка —
карточка на странице «Рассылки».

**Квиз-подбор** (`quiz`, `core/quiz/quiz.ts`): кнопка «🧩 Подобрать товар» в
меню Telegram-бота, до 5 вопросов с вариантами кнопками; у варианта —
теги, ответы копятся в `state.quiz_tags`, в конце товары получают очки за
теги в названии, ключевых словах и описании, бот показывает до трёх лучших
(в продаже и на складе). Настройка и проверка подбора — страница
`/admin/quiz`.

Один ключ на всех клиентов, изоляция по профилю (`core/tenant/zernio-accounts.ts`):
аккаунт может принадлежать только одному клиенту — синхронизация чужой
аккаунт пропускает и показывает конфликт, оператор чужой id сохранить не
может, справочник на аккаунт с двумя владельцами отвечает «ничей»,
предполётная проверка такой дубль блокирует. Крон `health` раз в 15 минут
сверяет профили с Zernio (`channels/zernio/health.server.ts`): новый
аккаунт виден без кнопки, отвалившийся помечается и продавец получает
предупреждение в Telegram. Карточка клиента у оператора показывает
профиль, аккаунты со статусом и временем последнего события.

WhatsApp-рассылки шаблонами Meta (`wa_broadcasts`): та же очередь
`broadcasts`/`broadcast_recipients` с `channel = whatsapp` — аудитория из
`bot_users.platform = whatsapp` (номер из `contact_phone` или `wa_<номер>`,
минус `opt_out` и `whatsapp_bot_excluded_phones`), отправка через
`POST /inbox/conversations` с `templateName` (`channels/zernio/jobs.ts`),
коды Meta «не в WhatsApp» (131021/131026) считаются как «заблокировали».
Шаблоны — локальная копия `whatsapp_templates` (`core/whatsapp/templates.ts`):
синхронизация из Meta и заявка на новый шаблон из админки
(`channels/zernio/templates.server.ts`), вердикт ревью — вебхуком
`whatsapp.template.status_updated`. Крон `broadcast` гоняет пакеты Telegram
и WhatsApp по одному на клиента; в WhatsApp нет «себе на пробу».

Автоматизация комментариев Instagram (модуль `instagram`): правила
Comment-to-DM живут у Zernio (`/comment-automations`), наши дополнения —
двухшаговая DM, текст второго сообщения, публичная просьба написать в
директ — в `app_settings.ig_comment_automations_meta` тем же ключом, что в
v1 (клиент переезжает без потери настроек). Чистые правила —
`core/instagram/comment-rules.ts` (совпадение слов, окно 5 минут…6,5 дней,
статусы комментариев, id постов, тело правила), оркестрация —
`channels/zernio/automations.server.ts`: `comment.received` → второе
сообщение с кнопками (или очередь `two_step_dm_pending` в `zernio_logs`,
доставка первым же DM покупателя), крон `comment-dm-fallback` раз в 15
минут дошлёт пропущенные private-reply с эскалацией (inbox в существующий
диалог обычной отправкой (без тега HUMAN_AGENT: он у Meta только для ответа
живого сотрудника), публичный ответ, просьба написать первым; журнал
`comment_dm_fallback_sends`), догоняющая рассылка из `/admin/instagram`.
Таблицы `comment_automation_settings` и `zernio_automations` в живой базе
нет — не используются.

Новому покупателю магазин в Direct/WhatsApp первым делом показывает выбор
языка на четырёх языках (`languagePickerText`, `needsLocalePick`); после
двух нераспознанных ответов — язык магазина и каталог, шаг не держит
человека вечно. Повторно — по слову «язык».

В WhatsApp разделы, товары, страна и языки — списками Meta (interactive
list, `whatsappList` в `shop-flow.ts`, до десяти строк с навигацией):

сценария — `STEP:<n>`, который разбирается как набранная цифра. В
Instagram по-прежнему нумерованный текст и три кнопки.
