# Переключение прода с v2 на v3

Для Якова. v3 — это v2 (коммит 53b1f6a) плюс доработки; схема базы та же,
база та же, клиенты те же. Решение Якова (03.10.2026, 16:53): в конце v3
вливается в репозиторий `FrogFlow/frogflow-v2`, а прод остаётся в **том же
проекте Vercel** и на том же домене. Нового проекта и переноса домена нет:
меняется только то, какой коммит собирается в production. Всё, что ждёт слова
Якова, помечено **«ждёт слова Якова»**: без него ничего не трогаем (v2
заморожен, Vercel и живая база — тоже).

## Что нового в v3 относительно v2

Продавцу и покупателям:

- **Онлайн-школа:** тарифы ниши на `/for/courses`, групповой чат потока,
  кураторы и нагрузка на странице ДЗ, перевод ученика в другой поток, ручное
  продление доступа, выгрузка учеников в CSV, сертификат (PDF) и страница
  проверки, голосовые и видео в домашних заданиях, чеклист запуска школы.
- **Деньги и чеки:** сверка получателя в автопроверке чека, чек старше 3
  суток уходит продавцу, ручная правка баллов с журналом, ошибки чтения базы
  в оплатах, возвратах и остатках больше не превращаются в «нет данных».
- **Кроны не дублируют сообщения**, если идут одновременно (поздравления,
  VIP, дайджест, уведомления о заказах, подписки платформы, удаление магазина).
- **Сайт:** SEO-статьи `/blog` на 4 языках, метатег Яндекс Вебмастера.

Оператору:

- **«Лиды»:** воронка, ИИ-оценка, черновик первого сообщения, автопоиск и
  ежедневный крон. Крон **выключен** флагом `v3_lead_cron` в карточке
  «Конвейер лидов», включать только когда v1 перестал вести лидов.
- **`/api/health`** отдаёт `version: 3` и список переменных окружения
  (только «задана / нет»); без обязательной переменной отвечает `ok: false`.
- **Режим предпросмотра** `PREVIEW_READONLY=1` (только для превью-деплоев):
  кроны и вебхуки не работают, отправка и платные вызовы (ИИ, Vision, ApiPay,
  push) выключены.
- Новый крон в `vercel.json`: `/api/cron/leads` (`0 6 * * *`, это UTC: 11:00 по Алматы, ежедневно).

Для разработчика: `npm run verify` (lint, типы, тесты, сборка, сертификат из
собранного сервера, проверка вывода под Vercel), `npm run smoke` (поднять
собранный сервер на подставной базе и пройти основные адреса).
Подробнее — `docs/ROADMAP.md`, раздел «v3».

## Переменные окружения

Проект Vercel остаётся прежним, поэтому переменные уже стоят и переносить их
не нужно. Относительно v2 в `src/config/env.ts` v3 добавил только две
необязательные (сверено: `git diff 53b1f6a HEAD -- src/config/env.ts`
добавляет `YANDEX_VERIFICATION` и `PREVIEW_READONLY`, обязательных новых нет):

| Переменная            | Где задать                                                | Что делает                                                                                                               |
| --------------------- | --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `YANDEX_VERIFICATION` | Production, по желанию                                    | метатег подтверждения сайта в Яндекс Вебмастере                                                                          |
| `PREVIEW_READONLY`    | **только Preview = `1`**; в Production не задавать совсем | `1` отключает работу кронов и вебхуков (они отвечают 200 без работы), отправки и платные вызовы выключены; вход работает |

**`PREVIEW_READONLY=1` в Production молча остановит прод:** вебхуки Telegram и
Zernio, кроны, отправка сообщений покупателям. Перед вливанием проверить, что
в Vercel → Settings → Environment Variables у этой переменной отмечена только
среда Preview.

Обязательные (без них платформа не стартует): `APP_URL`, `SUPABASE_URL`,
`SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_JWT_SECRET`,
`SECRETS_KEY`, `SESSION_SECRET`, `WEBHOOK_SECRET`, `CRON_SECRET`. У v2 они уже
заданы; `SECRETS_KEY` и `SESSION_SECRET` не менять: иначе токены ботов в базе
не расшифруются, а продавцы разлогинятся. Остальные включают функции
(оператор, Zernio, ApiPay, ИИ, Vision, почта, push, Sentry, курс ВТБ): полный
список с пояснениями — `src/lib/env-report.ts`. Среда Preview должна получить
те же значения, что Production (галочка Preview у каждой переменной), иначе
предпросмотр не стартует; `/api/health` покажет, чего не хватает.

## Порядок переключения

Делать в тихий час (см. «Тихий час» в `docs/MIGRATION.md`). Шаги 1 и 3–5 ниже
**ждут слова Якова** на сам день переключения.

0. **Предусловия в репозитории** (ничего в Vercel не трогают). В клоне v3:
   ```
   git remote add v2 https://github.com/FrogFlow/frogflow-v2.git
   git fetch v2 master
   git merge-base --is-ancestor v2/master master && echo "fast-forward: можно"
   git log --oneline master..v2/master
   ```
   Первая проверка должна сказать «можно» (v3 содержит всю историю v2), вторая
   — вывести пусто: все срочные правки v2 уже есть в v3. Иначе (в v2 после
   53b1f6a что-то влили) — принести эти коммиты в v3 обычным merge, без
   перебазирования (CLAUDE.md), прогнать `npm run verify` и проверить снова.
   Пока проверки не прошли, вливание — не fast-forward, и делать его нельзя.
   Затем `npm run verify` и `npm run smoke` на этом же коммите (smoke поднимает
   собранный сервер на подставной базе).
1. **Снимок «до».** Копия базы по `docs/BACKUP.md`, запись: какие клиенты на
   v2 (`served_by = "v2"`) и номер текущего production-деплоя в Vercel (по нему
   откат, раздел ниже). v3 пойдёт по тем же клиентам — отдельно никого
   переключать не нужно.
2. **Переменные.** В проекте v2: `PREVIEW_READONLY=1` только для Preview,
   `YANDEX_VERIFICATION` по желанию для Production; проверить, что у
   `PREVIEW_READONLY` нет Production (раздел выше).
3. **Предпросмотр на том же проекте** (**ждёт слова Якова**: пуш в v2). Ветка
   v3 уходит в репозиторий v2 не в master: `git push v2 master:refs/heads/v3-preview`.
   Vercel соберёт Preview-деплой этого коммита; production не меняется. Кроны
   Vercel идут только у production-деплоя, а вебхуки и отправки Preview
   выключены `PREVIEW_READONLY`. Проверить адрес предпросмотра, только чтением:
   - `/api/health` → `ok: true`, `version: 3`, `missingRequired` пуст;
   - главная, `/for/courses`, `/blog`, `/sitemap.xml`, витрина демо `/s/<адрес>`;
   - вход оператора и продавца демо-клиента.
4. **Вливание** (**ждёт слова Якова**). Fast-forward без force:
   `git push v2 master:master`. Если GitHub отказал — шаг 0 не пройден,
   принудительно не пушить (force-push только со словом Якова). Vercel
   соберёт production из этого коммита; кроны берутся из `vercel.json` нового
   деплоя, так что v2 и v3 одновременно не работают: один проект — один набор
   кронов. Окно — только пока идёт сборка: старый деплой ещё отвечает, потом
   домен переходит на новый. Новая запись в `vercel.json` — `/api/cron/leads`;
   она ничего не делает, пока выключен флаг `v3_lead_cron`.
5. **Вебхуки.** Домен и `APP_URL` те же, поэтому адреса вебхуков Telegram,
   Zernio и ApiPay не меняются. Крон `ensure-webhook` раз в час сам
   проверяет вебхуки Telegram; не ждать часа — запустить вручную
   (`/api/cron/ensure-webhook` с `CRON_SECRET`). У клиентов на Instagram и
   WhatsApp открыть «Вебхук Zernio»: если статус не «привязан», нажать «Привязать».
6. **Проверить прод после деплоя**, только чтением:
   - Vercel → Deployments: production — коммит v3, сборка зелёная;
     Settings → Cron Jobs показывает `/api/cron/leads` среди кронов;
   - `/api/health` на домене: `ok: true`, `version: 3`;
   - `npm run smoke` на прод **не направляется** (подставная база; он пройден
     на шаге 0). Прод проверяем руками: главная, `/s/…` у Print KZ Art и
     Education Bot, вход продавца Education Bot;
   - в Sentry за первые 15 минут нет новых ошибок, а сообщений покупателям
     дважды не пришло (смотреть историю заказа).
7. **Через сутки:** убедиться, что ночные кроны (`retention`, `vip`, подписки)
   прошли один раз; затем — по слову Якова — включить `v3_lead_cron`, если
   лидов больше не ведёт v1.

## Откат

Откат — **Instant Rollback** в Vercel: Deployments → прежний production-деплой
v2 (номер записан на шаге 1) → Instant Rollback. Домен сразу отдаёт прежнюю
сборку, git ничего не перематывает (master v2 остаётся на v3, force-push не
нужен). Кроны берутся из деплоя, на который откатились: проверить в Settings
→ Cron Jobs и в течение суток следить, что кроны идут по одному разу. После
отката Vercel может перестать сам назначать домену новые деплои: проверить в
Settings → Domains и, когда готовы к повторному переходу, назначить деплой
вручную (Promote). Данные остаются в той же базе, но v2 **не знает** части
того, что писал v3. Перечень ведёт `src/core/courses/compat-v2.test.ts`
(реестр `V3_ONLY`); если школа на v3 не запускалась, на это можно не смотреть.

**Оговорка про данные школы.** Пока школа на v3 не запущена (первый клиент —
середина октября), таблица ниже пуста и откат чистый. После запуска школы
откат возвращает код v2, а записанное v3 остаётся в базе и v2 его не
понимает:

| Что v3 записал                                             | Что произойдёт на v2                                                                                                             |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `course_run_*`.`until` (ручное продление доступа)          | v2 закроет канал по сроку тарифа, а не по продлению; при отметке урока потеряет поле. Продлённым ученикам вернуть доступ вручную |
| поток `chat` (групповой чат потока)                        | v2 сотрёт его при следующем сохранении курса в админке; новых ссылок в чат не выдаст, исключать из чата не будет                 |
| `course_invg_*` (ссылки в чаты потоков)                    | v2 их не читает: из чатов потоков по окончании срока никого не исключит                                                          |
| `course_cur_*` (кураторы)                                  | v2 не закрепляет работы за кураторами                                                                                            |
| `course_cert_no` (счётчик сертификатов)                    | v2 сертификаты не выдаёт; выданные остаются                                                                                      |
| события `access_extended`, `cohort_moved` в истории заказа | v2 показывает голое название события, на работу не влияет                                                                        |
| флаг `v3_lead_cron` и данные «Лидов»                       | v2 их не читает; **до отката выключить `v3_lead_cron`**                                                                          |

Всё остальное v3 пишет в форматах v2 и откат переносит без потерь. Починить
v2 так, чтобы он сохранял неизвестные поля прохождения и учитывал `until` в
кроне окончания доступа, можно маленькой правкой `parseRun` и
`core/courses/reminders.server.ts` — **ждёт слова Якова** (v2 заморожен).

После отката: проверить `/api/health`, вебхуки (шаг 5) и
в течение суток следить, что кроны идут по одному разу.
